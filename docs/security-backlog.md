# Security backlog

Medium and low findings from the security reviewer that didn't block a merge. High findings are fixed before merging and don't land here.

## Open

- **[low] A config without `popup` fails late.** `popup` is required by the type, but `loadRestaurant` doesn't check the JSON, so a hand-edited config missing it loads fine and then throws at the first `place_order`. It should fail at startup with a clear message. Found reviewing `feat/cleanup` (wave 0). Test to add in `test/robustness.test.ts`: loading a config with `popup` removed throws `/popup/`.
- **[medium] `/api` accepts form-encoded POSTs and doesn't check Origin.** `src/server.ts` mounts `express.urlencoded`, so a hostile page can send a plain form POST to any `/api` route, and the JSON content type the web client sends doesn't help. Harmless for the guest chat today. Owner routes behind a session cookie (wave 2, package D) would be open to cross-site request forgery. Before D: require `application/json` on `/api` POSTs (415 otherwise), check `Origin` or `Sec-Fetch-Site`, and set the session cookie to `SameSite=Lax` or stricter. Found reviewing `feat/web-shell` (wave 1). Test: a form-encoded POST to `/api/chat` gets 415.
- **[medium] The per-phone preorder cap is easy to get around.** It compares the last 10 digits, so "555-0100" and "510-555-0100" count as different numbers, and nothing verifies a phone anyway. It slows down honest repeat orders and nothing more. Either require 10 digits for preorders or compare fewer, and don't describe it as abuse protection. Found reviewing `feat/guardrails` (wave 1). Test: two orders on "510-555-0100" and "(510) 555-0100" and then a third on "555-0100" should be refused.
- **[low] `compact` assumes one process.** It rewrites the ledger from memory and renames over the file, so lines a second process appended in the meantime are lost. It also drops lines of unknown kinds without logging how many, and a crash mid-write leaves a `.tmp` file. Fine for one server per kitchen. Log the dropped count and say "one process per data dir" in the deploy notes. Found reviewing `feat/guardrails`.
- **[low] Without `DATA_DIR`, `./events.jsonl` is never trimmed.** Compaction only runs when the ledger is persistent, so a dev or demo run that falls back to the webhook file keeps guest names and phones there indefinitely. Found reviewing `feat/guardrails`.
- **[low] The privacy notice undersells what's kept.** It mentions name and phone. Order notes and the chat text (which often contains a phone number) are kept for the same period, and the owner can read them in the admin views. Say so on `/order` when wave 2 renders it. Found reviewing `feat/guardrails`.
- **[low] The kitchen file store doesn't fsync, and `events()` returns the live array.** A power cut right after an append or a catalog save can lose it, and a failed catalog write leaves `<kitchen>.catalog.json.tmp` behind. `events()` is typed `readonly` but callers can still change the array. Found reviewing `feat/kitchen-core` (wave 1).
- **[low] `maxBatch` hides its cap.** With a recipe that has no components, or plenty of stock, it returns the 10,000 search limit, which reads as a real answer. A NaN or fractional `limit` isn't clamped either. Return `Infinity` or a flag for "not limited by stock" before wave 2 shows it. Found reviewing `feat/kitchen-core`.
- **[low] No index fallback for the React app.** Express serves `web/dist` statically, so reloading `/count` or opening a shared `/order` link returns 404 once the build is served. Wave 2 (D or F) adds a GET fallback to `index.html` that skips `/api` and `/admin`. Found reviewing `feat/web-shell`.
- **[low] Frontend build hardening.** Set `build.sourcemap: false` explicitly in `web/vite.config.ts` so a later change can't ship source maps through `express.static`, and add `npm --prefix web audit --omit=dev` to CI. Found reviewing `feat/web-shell`.

The entries below come from the wave-1 pass over everything merged. Each has a test in `test/security-backlog.test.ts` marked `it.fails`: it passes while the bug exists and starts failing once it's fixed, at which point change it to `it` and move the entry out of this list.

- **[medium] Stock and plan maths trip over ids that are also `Object.prototype` names.** `onHand` in `src/kitchen/stock.ts` and `explode` in `src/kitchen/plan.ts` keep amounts in plain objects keyed by item and location id. A location called `constructor` gives an on-hand total of `"0function Object() { [native code] }10"`. An event for an item called `__proto__` writes its amount onto `Object.prototype`, so every other item at that location starts from it, in the whole process. `isStockEvent` and `validateCatalog` accept both. `src/kitchen/units.ts` already guards against this with `Object.hasOwn`. Nothing reaches these functions from a request yet, so it isn't a high, but wave 2 (E) feeds them names from chat and receipt text. Before then: use `Map` or `Object.create(null)`, and refuse ids that aren't kebab-case in `validateCatalog` and `FileStore.append`. Tests: the four under "kitchen stock" that mention `constructor` and `__proto__`.
- **[medium] A repeated order for the last of a batch is refused as sold out.** `placeOrder` in `src/domain/restaurant.ts` checks stock (line 153) before it looks for the same order from the same conversation (line 166). When a guest's order takes the last syrniki and the model repeats `place_order`, the second call fails with "sold out" instead of returning the original, and the guest can be told an order that exists didn't go through. The cutoff check has the same ordering. Move the duplicate check above the stock and cutoff checks. Test: "gives a retry its original order back even when that order took the last of the batch".
- **[medium] The per-conversation turn cap can't be reached at its default.** `guardedTurn` in `src/server.ts` counts guest messages in the session history, but `runTurn` trims that history to 40 messages, which is about 20 turns. With `MISE_MAX_TURNS` at its default of 30 the count never gets there, so one conversation can go on for as long as the rate limit and daily budget allow. The existing test sets the cap to 2. Keep a turn counter on the session instead of counting history. Test: "ends a conversation at the default 30 turns".
- **[low] The stock file is replayed without checking for repeated event ids.** `FileStore.append` skips ids it has in memory, but the constructor loads every line. Two processes on one data dir, or a restore that concatenates two copies, put the same confirmed event in the file twice and the next start counts it twice (360 eggs for a 180-egg delivery). Skip ids already seen while loading. Test: "counts an event once when its line is in the stock file twice".
- **[low] One bad order line in the ledger stops the server.** `Ledger` keeps any line with `kind: "order"` without looking at its `value`. A line with no value, or an order without `items`, makes `RestaurantStore.remaining` throw on every menu search, and once the line is older than the retention period `compact` throws inside `createApp`, so the server doesn't start. Check the shape on load and skip (and count) lines that don't fit, as `FileStore` does. Test: "starts up when the ledger has an order line with no order in it".
- **[low] Nothing slows down guesses at the admin token.** `/admin/api` answers 401 as fast as it's asked; the chat rate limiter doesn't cover it. A generated token is long enough that this doesn't matter, but wave 2 (D) replaces it with a passcode the owner types, which won't be. Rate limit failed sign-ins per IP when D lands. Test: "slows down someone guessing the admin token".
- **[low] The Today fixtures don't match what the kitchen core returns.** In `web/src/fixtures/ruki.ts`, `PrepTask.recipe` holds a display name and `PrepList` prints it, but `explode` returns the recipe id, so the wired screen would show `syrniki-batter`. The preorder rows are `{ name, window, items: [{ item, qty }] }` with first names, while a real `Order` has `pickupTime`, `items: [{ name, quantity }]`, the name exactly as the guest typed it, and the phone. The endpoint that feeds Today in wave 2 (F) should send the first name only and no phone, and look recipe names up from the catalog. Test: "names prep tasks the way explode does, by recipe id".

## Covered elsewhere

- **[low] Old reservation lines keep names and phones on disk.** Replay skips them, but they stay in old ledger files. `Ledger.compact` (wave 1, C2) rewrites the ledger from the entries it keeps, so these lines go the first time it runs.
