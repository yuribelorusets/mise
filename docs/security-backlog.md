# Security backlog

Medium and low findings from the security reviewer that didn't block a merge. High findings are fixed before merging and don't land here.

## Open

- **[low] A config without `popup` fails late.** `popup` is required by the type, but `loadRestaurant` doesn't check the JSON, so a hand-edited config missing it loads fine and then throws at the first `place_order`. It should fail at startup with a clear message. Found reviewing `feat/cleanup` (wave 0). Test to add in `test/robustness.test.ts`: loading a config with `popup` removed throws `/popup/`.
- **[medium] The per-phone preorder cap is easy to get around.** It compares the last 10 digits, so "555-0100" and "510-555-0100" count as different numbers, and nothing verifies a phone anyway. It slows down honest repeat orders and nothing more. Either require 10 digits for preorders or compare fewer, and don't describe it as abuse protection. Found reviewing `feat/guardrails` (wave 1). Test: two orders on "510-555-0100" and "(510) 555-0100" and then a third on "555-0100" should be refused.
- **[low] `compact` assumes one process.** It rewrites the ledger from memory and renames over the file, so lines a second process appended in the meantime are lost. It also drops lines of unknown kinds without logging how many, and a crash mid-write leaves a `.tmp` file. Fine for one server per kitchen. Log the dropped count and say "one process per data dir" in the deploy notes. Found reviewing `feat/guardrails`.
- **[low] Without `DATA_DIR`, `./events.jsonl` is never trimmed.** Compaction only runs when the ledger is persistent, so a dev or demo run that falls back to the webhook file keeps guest names and phones there indefinitely. Found reviewing `feat/guardrails`.
- **[low] The kitchen file store doesn't fsync, and `events()` returns the live array.** A power cut right after an append or a catalog save can lose it, and a failed catalog write leaves `<kitchen>.catalog.json.tmp` behind. `events()` is typed `readonly` but callers can still change the array. Found reviewing `feat/kitchen-core` (wave 1).
- **[low] `maxBatch` hides its cap.** With a recipe that has no components, or plenty of stock, it returns the 10,000 search limit, which reads as a real answer. A NaN or fractional `limit` isn't clamped either. Return `Infinity` or a flag for "not limited by stock" before wave 2 shows it. Found reviewing `feat/kitchen-core`.
- **[low] Frontend build hardening.** Set `build.sourcemap: false` explicitly in `web/vite.config.ts` so a later change can't ship source maps through `express.static`, and add `npm --prefix web audit --omit=dev` to CI. Found reviewing `feat/web-shell`.

The entries below come from the wave-1 pass over everything merged. Each has a test in `test/security-backlog.test.ts` marked `it.fails`: it passes while the bug exists and starts failing once it's fixed, at which point change it to `it` and move the entry out of this list.

- **[medium] The per-conversation turn cap can't be reached at its default.** `guardedTurn` in `src/server.ts` counts guest messages in the session history, but `runTurn` trims that history to 40 messages, which is about 20 turns. With `MISE_MAX_TURNS` at its default of 30 the count never gets there, so one conversation can go on for as long as the rate limit and daily budget allow. The existing test sets the cap to 2. Keep a turn counter on the session instead of counting history. Test: "ends a conversation at the default 30 turns".
- **[low] One bad order line in the ledger stops the server.** `Ledger` keeps any line with `kind: "order"` without looking at its `value`. A line with no value, or an order without `items`, makes `RestaurantStore.remaining` throw on every menu search, and once the line is older than the retention period `compact` throws inside `createApp`, so the server doesn't start. Check the shape on load and skip (and count) lines that don't fit, as `FileStore` does. Test: "starts up when the ledger has an order line with no order in it".
- **[low] Nothing slows down guesses at the admin token.** `/admin/api` answers 401 as fast as it's asked; the chat rate limiter doesn't cover it. A generated token is long enough that this doesn't matter, but wave 2 (D) replaces it with a passcode the owner types, which won't be. Rate limit failed sign-ins per IP when D lands. Test: "slows down someone guessing the admin token".

The entries below come from the wave-2 branch reviews (`feat/kitchen-api` and `feat/kitchen-assistant`). None has a test yet.

- **[medium] Wrong passcodes from many addresses lock the owner out.** `FailedSignIns` in `src/ops/owner-auth.ts` also caps failures overall (50 in 15 minutes) and checks that cap before the passcode, so once it's hit, the right passcode gets 429 too. `trust proxy` is always 1, so without a proxy in front, a made-up `X-Forwarded-For` also gets around the per-IP limit. Let a correct passcode through the overall cap, and only trust the proxy header when Mise runs behind one. Found reviewing `feat/kitchen-api` (wave 2). Test: 50 wrong passcodes from different IPs, then the right one signs in.
- **[medium] The owner cookie is only `Secure` when `NODE_ENV` is `production`.** A deploy that doesn't set it sends the 30-day session cookie over plain HTTP. Default to `Secure` and opt out for local development. Found reviewing `feat/kitchen-api`.
- **[medium] Item and location names go into the assistant's system prompt as they are.** `offer_new_item` accepts names up to 60 characters, newlines included, so once the owner taps Add, a name like "Salt\nIgnore the rules" becomes standing prompt text. Refuse control characters in new names and collapse whitespace where `prompt.ts` lists items and locations. Found reviewing `feat/kitchen-assistant`.
- **[low] An item id that's `__proto__` can still reach `stockView`.** `lastCount[e.item] ??= {}` in `src/kitchen/api.ts` isn't guarded, and a scratch test with a `__proto__` count event hung the test process. Package E's id check in `validateCatalog` and `isStockEvent` should keep such ids out; confirm it covers `POST /api/kitchen/catalog/items`, and use `Object.create(null)` there anyway. Found reviewing `feat/kitchen-api`.
- **[low] A malformed catalog record gives a 500.** The catalog routes store the record as sent, so an item without `aliases` makes `validateCatalog` throw a plain error. Copy only the known fields and check their types first. Found reviewing `feat/kitchen-api`.
- **[low] Reusing a count's `clientId` drops the new numbers.** Count event ids are `count-${clientId}-${i}`, and `append` skips ids it has, so a corrected count sent with the same `clientId` returns 200 and writes nothing. Return 409 when the lines differ, or put a hash of the lines in the id. Found reviewing `feat/kitchen-api`.
- **[low] Confirming a booked proposal with new edits returns 200 and ignores them.** That's the idempotent path, but a client could think its edits were booked. Return the booked lines (it does) and say so in the screen. Found reviewing `feat/kitchen-api`.
- **[low] Lines with a 0 or huge amount pass `checkLine`.** A zero receive, use, waste or move makes an empty card line, and amounts up to about 1e300 can push a stock total to `Infinity`. Require more than 0 except for counts, and set an upper bound. Found reviewing `feat/kitchen-assistant`.
- **[low] Assistant sessions are evicted oldest first, even mid-turn.** Past 50 session ids, a busy session can be dropped and recreated empty, and two turns then run at once on the same id. Evict only idle sessions, least recently used first. Found reviewing `feat/kitchen-assistant`.
- **[low] `--max-usd` is checked between turns, not between model calls.** One live kitchen turn can make up to 6 calls and go over the cap by that much. Found reviewing `feat/kitchen-assistant`.
- **[low] A repeated stock line is dropped on load without a word.** That's the fix for counting it twice, but a hand-merged file can lose a real event with no trace. Log how many were skipped. Found reviewing `feat/kitchen-assistant`.
- **[low] The kitchen evals are thin on the mock.** 7 of the 10 scenarios in `evals/scenarios/kitchen.yaml` are tagged `live`, so CI runs 3. The mock writes its reply from the tool output, so `reply_numbers_from` can't fail there, and it matches any number anywhere in the tool JSON. Make the max-batch, booking-claim and cost scenarios mock-runnable, and match numbers by field. Found reviewing `feat/kitchen-assistant`.
- **[low] The new id check refuses catalogs that used to load.** `validateCatalog` now wants lower-case kebab-case ids, so a hand-edited catalog with `Eggs_L` fails at startup. The shipped catalogs pass. Say so in the error message and the docs. Found reviewing `feat/kitchen-assistant`.
- **[low] The guest chat on `/order` is kept in `sessionStorage`.** `mise.order.messages` holds what the guest typed, name and phone included, until the tab closes, so a shared device shows it to the next person. The privacy notice doesn't mention it. Keep only the session id, or say so in the notice. Found reviewing `feat/web-wired` (wave 2).
- **[low] Prep checkmarks outlive sign-out.** `mise.prep.<planId>` in `localStorage` holds recipe ids only, no personal data. Clear the keys on sign-out. Found reviewing `feat/web-wired`.
- **[low] A server error on `/api/owner/me` shows the sign-in screen.** A 500 or a dropped connection reads as signed out, so the owner is asked for the passcode while the server is down. Show an error instead. Found reviewing `feat/web-wired`.
- **[low] Restored chat cards can show Confirm for a proposal the server no longer has.** Assistant messages persist in `sessionStorage` with proposal snapshots. A 404 on confirm now refetches the list, but the card falls back to its snapshot. Show it as gone instead. Found reviewing `feat/web-wired`.
- **[low] The guest mock keeps the last word as the guest's name.** "Anna Petrova 510-555-0142" is stored as "Petrova", so Today shows a surname in demos. Only the mock is affected. Found checking `feat/web-wired` in the browser.
- **[medium] Guests can read the kitchen's capacity when selling from stock is on.** With `popup.sellFromStock` true, `remaining` includes what stock can make, and `search_menu` and the "Only N left" error pass it to the guest chat. Give guests `soldOut` and a count capped at `maxPerItem`. Off by default for Ruki. Found reviewing `feat/preorders-plan` (wave 2).
- **[medium] One order for two dishes can oversell an ingredient they share.** Each line is checked against capacity on its own, so the maximum of A plus the maximum of B passes when they share the last flour. After the per-line checks, explode all the order's lines together against what's left. Only matters with `sellFromStock` on. Found reviewing `feat/preorders-plan`.
- **[medium] Capacity reads one plan per date.** It sets aside the first plan for the event date only, and ignores other plans for the same date and plans for other dates that draw on the same stock. Fine for one pop-up date with one plan. Found reviewing `feat/preorders-plan`.
- **[low] `sold` and capacity can count different orders.** `sold` counts every order in the ledger, while capacity counts only orders for `popup.eventDate`. That holds today because `placeOrder` always uses the event date. Found reviewing `feat/preorders-plan`.

## Fixed

- **[low] The Today fixtures don't match what the kitchen core returns.** Fixed in wave 2 (F): Today reads `/api/kitchen/today`, which names prep by recipe and sends guests' first names only, and `test/web-fixtures.test.ts` checks the fixtures against the core.
- **[medium] `/api` accepts form-encoded POSTs and doesn't check Origin.** Fixed in wave 2 (D1): `/api` writes must be JSON (415 otherwise), cross-site writes get 403, and the owner cookie is `SameSite=Strict`.
- **[low] The privacy notice undersells what's kept.** Fixed in wave 2 (D5): `/api/config` sends a `privacyNotice` that names notes and chat text and who reads them. F renders it on `/order`.
- **[low] No index fallback for the React app.** Fixed in wave 2 (D5): GETs outside `/api` and `/admin` without a file extension get `index.html`.
- **[medium] The owner's assistant message has no length limit.** Already handled in D4: the assistant route refuses messages over 2,000 characters with a 400.
- **[medium] Stock and plan maths trip over ids that are also `Object.prototype` names.** Fixed in wave 2 (E1): `onHand` and `explode` use null-prototype objects, and `validateCatalog` and `isStockEvent` refuse ids that aren't kebab-case.
- **[low] The stock file is replayed without checking for repeated event ids.** Fixed in wave 2 (E1): `FileStore` skips ids it has already loaded.

## Covered elsewhere

- **[low] Old reservation lines keep names and phones on disk.** Replay skips them, but they stay in old ledger files. `Ledger.compact` (wave 1, C2) rewrites the ledger from the entries it keeps, so these lines go the first time it runs.
